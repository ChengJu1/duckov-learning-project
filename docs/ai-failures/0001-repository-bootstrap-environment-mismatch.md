# AI 失败案例：仓库初始化环境不一致

## 基本信息

任务目标：从空目录初始化 Git 仓库，并首次上传到 GitHub。

发生了什么：Codex 沙箱账户创建了 `.git`，用户账户随后被 Git 的所有者安全检查阻止；修复信任设置后，本机网络又无法直连 GitHub。改用网页上传产生了与本地不同的提交历史，之后才通过代理合并两边历史。

预期结果：本地初始化、首次提交、绑定远程并一次推送成功。

实际结果：经历了所有者检查、DNS 错误、443 端口阻断、网页上传和历史合并，才完成同步。

当时提供了哪些上下文：Windows 项目目录、GitHub 空仓库地址、Git 可用状态和项目协作要求。

缺失了哪些信息：开始时不知道 `.git` 会由不同的沙箱账户创建，也不知道本机访问 GitHub 必须使用 `127.0.0.1:7897` 代理。

影响了哪些模块：仅影响版本控制与仓库初始化流程，没有影响游戏代码。

## 三个 Why

Why 1：为什么直接出现错误？

Git 仓库由沙箱账户创建，实际用户账户不是目录所有者；同时，默认网络路径无法连接 GitHub。

Why 2：为什么系统没有提前避免错误？

初始化前只检查了 Git、Python 和 GitHub CLI，没有同时检查执行账户、目录所有者、GitHub DNS、443 连接和本地代理。

Why 3：为什么当前工程流程无法发现或阻止它？

仓库初始化清单尚未建立，上传方案也没有规定“本地提交必须先验证网络再创建远程历史”。

## 分析

问题分类：工具限制 / 任务规划 / 测试反馈

已确认事实：

- Git 报告仓库所有者与当前用户不同。
- `github.com` 一度被系统 DNS 解析为 `127.0.0.1`。
- 更换 DNS 后，直连 GitHub 443 仍失败。
- 本地代理 `127.0.0.1:7897` 可以访问 GitHub。
- 网页端和本地端的文件正文一致，`prompt.md` 仅有 CRLF/LF 差异。

基于现象的推测：当前网络环境对 GitHub 直连进行了限制，具体限制位置尚未确认。

需要进一步验证的假设：更换网络后是否可以不使用代理访问 GitHub。

可能涉及的底层原理：Git 使用提交对象的父提交、文件树、作者和时间共同计算提交标识。即使文件相同，网页端重新提交也会产生不同历史；两个没有共同父提交的分支需要显式合并。

## 改进

临时修复：为项目目录配置 Git `safe.directory`；使用本地 HTTP 代理访问 GitHub；验证文件仅有换行符差异后，用合并提交连接本地和远程历史。

长期解决方案：在仓库初始化前增加账户、所有权、DNS、443 连接、代理和换行符检查；优先保证命令行推送通路可用，再创建远程提交。

如何验证改进有效：在新测试目录按检查清单初始化仓库，应能由用户账户执行 `git status`，并通过代理完成 `git ls-remote`、`fetch` 和 `push`。

这个案例值得学习的知识：Git 对象与分支历史、Windows 文件所有权、DNS、HTTP 代理，以及为什么“文件相同”不等于“提交相同”。

这个案例在面试中可以怎样讲：说明如何依据错误信息逐层区分仓库权限、DNS、TCP 和 Git 历史问题，并用内容差异验证避免覆盖远程数据。
